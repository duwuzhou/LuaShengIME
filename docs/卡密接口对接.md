# 卡密接口对接文档

## 概述
当前服务端已提供两类卡密接口：

1. 首次兑换接口：用户输入卡密后调用。
2. 二次校验接口：应用启动或页面恢复后自动调用，用于确认会员状态仍然有效。

默认服务端基地址：

```text
https://km.moluhualuo.top
```

相关客户端实现：

- `IME/IME/Features/Settings/KamiVipActivity.cs`
- `IME/IME/Features/Settings/KamiVipVerificationCoordinator.cs`
- `IME/IME/Features/Settings/KamiVipConfig.cs`

## 1. 首次兑换接口
请求地址：

```http
POST /api/redeem-code
Content-Type: application/json
```

完整地址：

```text
https://km.moluhualuo.top/api/redeem-code
```

请求体：

```json
{
  "code": "YOUR_KAMI_CODE",
  "user_ref": "com.hualuo.luanshenIME:deviceUid",
  "device_uid": "deviceUid"
}
```

字段说明：

- `code`：用户输入的卡密。
- `user_ref`：客户端生成的用户标识，格式建议为 `包名:设备ID`。
- `device_uid`：设备唯一标识，默认优先使用 Android ID。
- `user_id`：可选。若客户端已保存服务端用户 ID，可在后续请求中一并上传。

成功响应示例：

```json
{
  "message": "Redeemed successfully.",
  "user_id": 123,
  "vip_expires_at": "2026-12-31T23:59:59.000000Z"
}
```

服务端行为说明：

- 未激活卡密不会因为时间流逝自动过期。
- 卡密首次激活后，才开始根据卡密面值计算到期时间。
- 已激活卡密在未到期前允许重复使用，但仅允许同一台已绑定设备。
- 同设备重复使用不会再次叠加会员时长。

成功后客户端应保存：

- `user_id`
- `vip_expires_at`
- `device_uid`
- 最近一次校验时间

## 2. 二次校验接口
请求地址：

```http
POST /api/verify-vip
Content-Type: application/json
```

完整地址：

```text
https://km.moluhualuo.top/api/verify-vip
```

建议触发时机：

- `KamiVipActivity`
- `MainActivity`
- `SettingsActivity`
- `ShortcutManagerActivity`
- `PredictionManagerActivity`
- `QuickSymbolEditorActivity`

建议客户端在 `OnResume` 时触发一次，并按 5 分钟间隔继续校验。

请求体：

```json
{
  "user_id": 123,
  "user_ref": "com.hualuo.luanshenIME:deviceUid",
  "device_uid": "deviceUid"
}
```

字段说明：

- `user_id`：优先使用。首次兑换成功后建议长期保存。
- `user_ref`：当客户端尚未拿到或未能恢复 `user_id` 时，用于回查自动创建用户。
- `device_uid`：必填，用于校验是否为已绑定设备。

成功响应示例：

```json
{
  "message": "ok",
  "user_id": 123,
  "vip_expires_at": "2026-12-31T23:59:59.000000Z",
  "is_active": true,
  "active": true
}
```

失效响应示例：

```json
{
  "message": "VIP expired.",
  "user_id": 123,
  "is_active": false,
  "active": false
}
```

服务端校验规则：

- 优先按 `user_id + device_uid` 校验。
- 若未传 `user_id`，服务端会尝试按 `user_ref + device_uid` 回查自动创建用户。
- 仅当“当前用户 + 当前设备”下存在未过期、已激活、已绑定的卡密时，才返回有效。
- 若设备与首次绑定设备不一致，返回 `409 Device mismatch.`。
- 若商户被禁用，返回 `403 Merchant disabled.`。
- 若当前会员已过期，返回 `410 VIP expired.`。

兼容字段：

- `is_active`
- `active`

客户端建议同时兼容这两个字段，只要任意一个明确为 `false`，就按失效处理。

## 3. 状态码约定
兑换接口 `POST /api/redeem-code`：

- `200`：兑换成功。
- `404`：卡密不存在或用户不存在。
- `409`：卡密已使用但设备不匹配，或用户/商户关系不匹配。
- `410`：卡密已过期。
- `403`：商户禁用。
- `422`：参数校验失败。
- `429`：请求过于频繁。

二次校验接口 `POST /api/verify-vip`：

- `200`：会员有效。
- `403`：商户禁用，客户端应清空本地会员状态。
- `409`：设备不匹配，客户端应清空本地会员状态。
- `410`：会员已过期，客户端应清空本地会员状态。
- `404`：用户不存在，客户端应清空本地会员状态。
- `422`：参数校验失败，客户端仅记录日志，不立即清空本地状态。
- `429`：请求过于频繁，客户端应退避重试，不立即清空本地状态。

## 4. 返回字段建议
服务端当前返回字段如下：

```json
{
  "message": "ok",
  "user_id": 123,
  "vip_expires_at": "2026-12-31T23:59:59.000000Z",
  "is_active": true,
  "active": true
}
```

字段说明：

- `vip_expires_at` 使用 ISO 8601 UTC 时间，例如 `2026-12-31T23:59:59.000000Z`。
- `user_id` 为服务端稳定主键，客户端后续二次校验应优先使用。
- `message` 可直接用于日志记录和简单提示。

## 5. 客户端处理建议
- 首次兑换成功后，立即持久化 `user_id`、`vip_expires_at`、`device_uid`。
- 二次校验时优先上传 `user_id`，不要只依赖 `user_ref`。
- 二次校验成功后，刷新本地 `vip_expires_at`。
- 当二次校验返回 `403`、`404`、`409`、`410` 时，立即清空本地会员状态。
- 当接口返回 `422`、`429` 或网络异常时，仅记录日志并保留当前本地状态，等待下一次重试。
- 同一设备上的已激活卡密可在未过期前重复校验通过；更换设备后不应继续视为有效。

## 6. 对接建议
- 客户端必须长期保存 `user_id`，这是二次校验的主路径。
- `user_ref` 作为兜底参数保留，避免本地数据迁移或升级时丢失 `user_id` 后无法恢复。
- 校验轮询频率不要过高，建议保持 5 分钟一次，并结合应用前后台状态控制。
- 若客户端已有本地过期判断，仍应以服务端 `verify-vip` 结果为准。
